                Dynamic Track Switching for MOQT relays
                     draft-wilaw-moq-dts4moq-latest

Abstract

   This document specifies Dynamic Track Switching (DTS) mechanisms for
   Media over QUIC Transport (MOQT).  DTS enables relays to dynamically
   select which groups to forward from a set of subscriptions based on
   available bandwidth, original publisher or end subscriber-defined
   priorities, supporting scenarios such as adaptive bitrate streaming
   and multi-participant video conferencing and others.  Two mechanisms
   are defined: (1) DTS within a single switching group using either
   Switching-Set-Assignment parameters or Track Filters per subscription
   that reference publisher track properties, and (2) DTS across
   multiple switching groups using Track Filters with Subscribe
   Namespace.  Publishers advertise track properties such as Throughput
   and SwitchingSetID in PUBLISH messages, which relays use for
   selection decisions.  Additionally, client hint parameters allow
   subscribers to influence relay selection decisions while maintaining
   bandwidth safety guarantees.  The document further describes relay
   bandwidth allocation strategies and degradation algorithms for
   adaptive bitrate streaming scenarios.

1.  Introduction

   This draft adds the capability of Dynamic Track Switching (DTS) to
   Media over QUIC Transport [MOQT].  Dynamic Track Switching allows a
   relay to dynamically switch which groups from what tracks are
   forwarded from among a set of subscriptions.  One use-case enabled by
   DTS is Adaptive Bitrate Streaming (ABR), in which time-aligned media
   tracks are switched at group boundaries based upon available
   throughput estimates.

   DTS operates at two levels:

   1.  *Single Switching Group*: Multiple quality variants of the same
       content (e.g., 1080p, 720p, 480p of a single video stream) are
       grouped together, and the relay selects the best quality that
       fits within available bandwidth.

   2.  *Multiple Switching Groups*: Multiple independent content streams
       (e.g., video from different participants in a conference) each
       have their own quality variants.  The relay must allocate
       bandwidth across all streams and select appropriate quality
       levels for each.

   This document defines two design approaches for single switching
   groups (Switching-Set-Assignment and Track Filter per subscription)
   and one approach for multiple switching groups (Track Filter with
   Subscribe Namespace).

2.  Use Cases

   This section describes several use cases that motivate Dynamic Track
   Switching, along with the requirements each places on publishers,
   subscribers, and relays.

2.1.  Adaptive Bitrate Streaming (ABR)

2.1.1.  Description

   In adaptive bitrate streaming, a single media source (e.g., a live
   video stream) is encoded at multiple quality levels (renditions) with
   different bitrates and resolutions.  The goal is to deliver the
   highest quality rendition that the network path can sustain at any
   given moment.  When bandwidth decreases, the system should switch to
   a lower quality rendition to avoid rebuffering.  When bandwidth
   increases, it should switch to a higher quality rendition to improve
   viewer experience.

2.1.2.  Requirements

   *Original Publisher*:

   *  MUST publish multiple time-aligned renditions of the same content

   *  MUST ensure groups across renditions are temporally aligned to
      enable seamless switching

   *  SHOULD advertise throughput requirements for each rendition

   *  SHOULD indicate which tracks belong to the same switching set
      (alternate group)

   *End Subscriber*:

   *  MUST subscribe to all desired renditions within a switching set

   *  MUST indicate which subscriptions form a switching set for relay
      coordination

   *  MAY specify preferences such as maximum desired quality or
      bandwidth constraints

   *  SHOULD be prepared to decode any rendition within the switching
      set

   *Relay*:

   *  MUST track available bandwidth to each downstream subscriber

   *  MUST select exactly one rendition per switching set to forward at
      any time

   *  MUST switch renditions at group boundaries to maintain
      decodability

   *  SHOULD minimize switching latency when bandwidth changes

2.2.  Video Conferencing Grid Layout

2.2.1.  Description

   In a video conference with multiple participants, each participant's
   video may be displayed in a grid layout.  When many participants are
   present, not all videos can be displayed at full resolution due to
   screen real estate and bandwidth constraints.  The system needs to
   deliver multiple participant streams simultaneously, potentially at
   different quality levels based on their importance (e.g., active
   speaker at high quality, other participants at lower quality).

2.2.2.  Requirements

   *Original Publisher*:

   *  MUST publish multiple quality renditions for their media stream

   *  MUST ensure temporal alignment of groups across renditions

   *  SHOULD advertise throughput requirements for each rendition

   *  SHOULD indicate switching set membership for their renditions

   *End Subscriber*:

   *  MUST subscribe to multiple switching sets (one per participant)

   *  MUST indicate relative importance (weight/priority) of each
      switching set

   *  MAY send SUBSCRIBE_UPDATE messages to adjust priorities (e.g.,
      when active speaker changes)

   *  SHOULD specify total bandwidth budget or constraints

   *Relay*:

   *  MUST allocate forwarding capacity across multiple switching sets
      simultaneously

   *  MUST respect subscriber-indicated weights when selecting groups to
      forward

   *  MUST select one rendition per switching set based on allocated
      capacity

   *  SHOULD implement degradation based on relative weight when total
      capacity is insufficient

   *  SHOULD respond to SUBSCRIBE_UPDATE messages with minimal latency

2.3.  Screen Sharing with Video

2.3.1.  Description

   A participant shares their screen while also transmitting camera
   video.  The screen content may have different characteristics than
   camera video (e.g., higher resolution for text readability, lower
   frame rate acceptable).  The system needs to prioritize bandwidth
   between screen sharing and camera video based on content type and
   subscriber preferences.

2.3.2.  Requirements

   *Original Publisher*:

   *  MUST publish renditions for each content type (screen, camera)

   *  MUST ensure groups are temporally aligned within each content type

   *  SHOULD indicate content type characteristics including relative
      priorities per content type (e.g., screen vs camera) and per
      rendition within each type

   *  SHOULD advertise throughput requirements per rendition

   *End Subscriber*:

   *  MUST subscribe to switching sets for each desired content type

   *  MUST indicate relative weights between content types

   *  MAY specify minimum acceptable quality for critical content (e.g.,
      screen)

   *  MAY send SUBSCRIBE_UPDATE messages to adjust priorities based on
      presentation mode

   *Relay*:

   *  MUST manage multiple switching sets with potentially different
      priorities

   *  MUST select groups to forward based on content type priorities

   *  SHOULD respect minimum quality thresholds indicated in
      subscription parameters

   *  SHOULD degrade lower-priority content before higher-priority
      content

2.4.  VR/AR Streaming

2.4.1.  Description

   Virtual and augmented reality applications require streaming high-
   resolution immersive content while adapting to available bandwidth.
   Two key scenarios benefit from DTS: foveated rendering where quality
   varies based on gaze direction, and multi-layer environments where
   different scene elements have different quality requirements.

   In foveated rendering, a 360-degree video is divided into tiles.  The
   tile where the user is currently looking (determined by eye tracking)
   receives highest quality, while peripheral tiles receive lower
   quality.  As the user's gaze shifts, bandwidth allocation must
   dynamically shift between tiles.

   In multi-layer VR environments, background scenery may be rendered at
   lower quality while interactive foreground objects receive higher
   quality, with priorities adjusting based on user proximity and
   interaction state.

2.4.2.  Requirements

   *Original Publisher*:

   *  MUST publish multiple quality renditions for each tile or scene
      layer

   *  MUST ensure temporal alignment across tiles and quality levels

   *  SHOULD advertise throughput requirements per tile/quality
      combination

   *  SHOULD indicate tile spatial relationships or layer hierarchy

   *End Subscriber*:

   *  MUST subscribe to all tiles within the field of view

   *  MUST send SUBSCRIBE_UPDATE messages to adjust priority weights
      based on gaze direction or interaction state

   *  SHOULD specify gaze tile with significantly higher weight than
      peripheral tiles

   *  MAY specify minimum acceptable quality for peripheral tiles to
      avoid visible artifacts

   *Relay*:

   *  MUST respond rapidly to SUBSCRIBE_UPDATE messages containing
      updated priority weights

   *  MUST adjust group forwarding decisions across tile subscriptions
      when priority weights change

   *  SHOULD maintain subscriptions to adjacent tiles at lower priority
      to enable smooth transitions

   *  MUST switch forwarded renditions at group boundaries to ensure
      decodability

2.5.  Cloud Gaming

2.5.1.  Description

   Cloud gaming services stream rendered game video from servers to
   players.  The video stream must adapt to network conditions while
   balancing resolution, frame rate, and latency based on game type and
   player preferences.  Different game genres have different
   requirements: fast-paced action games prioritize frame rate and low
   latency, while strategy games may prioritize resolution.

   Additionally, different regions of the game screen may have different
   importance: the HUD (heads-up display) with critical game information
   may need guaranteed quality, while the main game world adapts to
   remaining bandwidth.

3.  DTS Within a Single Switching Group

   This section describes mechanisms for switching between quality
   variants of a single logical media stream.  Two design approaches are
   presented.

3.1.  Approach 1: Switching-Set-Assignment

   This approach uses explicit parameters to group subscriptions into
   switching sets and define selection criteria.

3.1.1.  Parameters

3.1.1.1.  SWITCHING-SET-ASSIGNMENT Parameter

   The SWITCHING-SET-ASSIGNMENT parameter (Type 0x41) MAY appear in a
   SUBSCRIBE or REQUEST_UPDATE message.  This parameter assigns the
   accompanying subscription to a DTS switching set and specifies
   selection criteria.

   The Switching Set ID can be obtained from two sources:

   1.  *From Catalog*: The MSF catalog [MSF] defines Alternate Groups
       that group tracks representing alternate versions of the same
       content (e.g., different bitrate renditions).  The subscriber MAY
       use the Alternate Group ID from the catalog as the Switching Set
       ID.

   2.  *Subscriber-chosen*: The subscriber MAY uniquely choose based on
       application-specific logic.

   The parameter body is serialized as follows:

   SWITCHING-SET-ASSIGNMENT {
     Switching Set ID (vi64),
     [Throughput Threshold (vi64),
     Selection Time Limit (vi64)]
   }

   *  *Throughput Threshold*: The minimum throughput, expressed in
      integer kilobits per second, necessary to select this
      subscription.  MUST be omitted if Switching Set ID is zero.

   *  *Selection Time Limit*: The maximum time in milliseconds the relay
      waits after the first candidate group arrives before disqualifying
      this subscription.  MUST be omitted if Switching Set ID is zero.

3.1.1.2.  DTS-ACTIVATION Parameter

   The DTS-ACTIVATION parameter (Type 0x43) MAY appear in a SUBSCRIBE or
   REQUEST_UPDATE message.  This parameter enables or disables dynamic
   track switching for a specified switching set.

   DTS-ACTIVATION {
     Switching Set ID (vi64),
     State (1)
   }

   *  *Switching Set ID*: An integer referencing a previously defined
      switching set.

   *  *State*: A value of 1 activates dynamic switching; 0 deactivates
      it.

3.1.2.  Subscriber Workflow

   To disable DTS: Send REQUEST_UPDATE with DTS-ACTIVATION { State: 0 }.

   To remove a track from set: Send REQUEST_UPDATE with SWITCHING-SET-
   ASSIGNMENT { Set ID: 0 } or send Unsubscribe for the corresponding
   track.

   To add a track to existing set: Send SUBSCRIBE with SWITCHING-SET-
   ASSIGNMENT pointing to existing set.

3.1.3.  Relay Workflow

   1.  Upon receiving SWITCHING-SET-ASSIGNMENT, add subscription to the
       specified switching set (create if needed).  Set Forward state to
       0.

   2.  Upon receiving DTS-ACTIVATION with State=1, begin active track
       selection.

   3.  When Object 0 of a new Group N arrives, run the Track Selection
       Algorithm.

3.2.  Approach 2: Track Filter Per Subscription

   This approach uses the TRACK_FILTER parameter on individual SUBSCRIBE
   messages to achieve similar functionality with a different control
   model.

3.2.1.  Parameters

3.2.1.1.  TRACK_FILTER Parameter

   The TRACK_FILTER parameter (Type 0x29) MAY appear in a SUBSCRIBE or
   REQUEST_UPDATE message.

   TRACK_FILTER {
     Type (vi64) = 0x29,
     Length (vi64),
     Property Type (vi64),
     MaxTracksSelected (vi64),
     MaxTimeSelected (vi64)
   }

   *  *Property Type*: Identifies the publisher track property used for
      selection.  This MUST reference Throughput (0x4B) property carried
      in the PUBLISH message.  The relay uses this property value when
      objects arrive to determine track selection.

   *  *MaxTracksSelected*: Maximum number of tracks from this filter
      group to forward concurrently.  For single-track ABR, this is
      typically 1.  This value MUST NOT exceed the MAX_TRACKS_SELECTED
      setup option value sent by the peer.  A value of zero is a
      protocol violation.

   *  *MaxTimeSelected*: Milliseconds a track remains selected without
      delivering a matching object.

3.2.2.  Publisher Track Properties

   Publishers MUST advertise track properties in PUBLISH messages that
   the relay uses for filter-based selection.  These properties follow
   the Track Properties mechanism defined in [MOQT].

3.2.2.1.  Throughput Property

   The Throughput track property (Type 0x4B) indicates the per-track
   throughput requirement.

   Throughput Property {
     Type (vi64) = 0x4B,
     Length (vi64),
     Throughput (vi64)
   }

   *  *Throughput*: The minimum throughput in kilobits per second
      required for this track.  The relay uses this value when objects
      arrive to determine whether a track can be selected based on
      available bandwidth.  When a subscription specifies Property Type
      0x4B in the TRACK_FILTER, the relay evaluates this property for
      track selection.

3.2.2.2.  SwitchingSetID Property

   The SwitchingSetID track property (Type 0x4D) groups tracks into
   switching sets for coordinated selection.

   SwitchingSetID Property {
     Type (vi64) = 0x4D,
     Length (vi64),
     SwitchingSetID (vi64)
   }

   *  *SwitchingSetID*: An integer identifying the switching set this
      track belongs to.  Tracks with the same SwitchingSetID are grouped
      together for selection.  The relay uses this value to associate
      subscriptions that should be evaluated together for DTS decisions.
      Publishers MUST include this property to enable track filter
      grouping.

   Publishers include these properties in PUBLISH messages to inform
   relays of the throughput requirements and switching set membership
   for each track variant.

3.2.3.  Subscriber Workflow

3.2.4.  Relay Track Filter Algorithm

   When a relay receives a subscription with TRACK_FILTER, it performs
   the following:

   1.  *Track Property Extraction*: When a PUBLISH message arrives, the
       relay extracts the track properties (e.g., Throughput,
       SwitchingSetID) and stores them for later selection decisions.

   2.  *SwitchingSetID Determination*: The relay determines the
       switching set for each subscription using the SwitchingSetID
       property (0x4D) from the publisher's PUBLISH message.

   3.  *Track Matching*: For each track that matches the subscription
       namespace prefix, the relay evaluates whether the track has the
       property referenced by the Property Type.

   4.  *Filter Set Assignment*: Tracks with the same SwitchingSetID are
       grouped into a filter set for coordinated selection.

   5.  *Selection on Object Arrival*: When objects arrive, the relay
       uses the Property Type values (e.g., Throughput from PUBLISH) and
       available bandwidth to select which track to forward.

on_publish(track, properties):
    # Store track properties for later selection
    track.throughput = properties.get(0x4B)  # Throughput property
    track.switching_set_id = properties.get(0x4D)  # SwitchingSetID property

on_subscribe_with_track_filter(subscription):
    filter_set = get_or_create_filter_set()

    for track in all_tracks:
        if track.namespace.matches(subscription.namespace_prefix):
            if track.has_property(subscription.track_filter.property_type):
                # Use publisher's SwitchingSetID from PUBLISH properties
                filter_set.add(track, track.switching_set_id)

on_object_arrival(track, object):
    filter_set = get_filter_set(track.switching_set_id)
    # Use track's Throughput property for selection
    run_track_filter(filter_set, available_bandwidth)

3.3.  Client Hints for DTS

   While DTS delegates switching decisions to the relay, subscribers may
   need to influence selection in certain scenarios.  This section
   defines optional client hint parameters that allow subscribers to
   guide relay decisions without taking full control.

3.3.1.  Use Cases for Client Hints

   1.  *User-initiated quality change*: User explicitly requests higher/
       lower quality

   2.  *Power/thermal constraints*: Device needs to limit decode
       complexity

   3.  *Data saving mode*: User wants to cap quality regardless of
       bandwidth

   4.  *Preview mode*: Temporarily pin low quality while seeking, then
       release

3.3.2.  DTS-QUALITY-HINT Parameter

   The DTS-QUALITY-HINT parameter (Type 0x4F) MAY appear in a SUBSCRIBE
   or REQUEST_UPDATE message to express subscriber preferences for
   quality selection.

   DTS-QUALITY-HINT {
     Type (vi64) = 0x4F,
     Length (vi64),
     Switching Set ID (vi64),
     Hint Type (vi64),
     Hint Value (vi64)
   }

   *  *Switching Set ID*: The switching set this hint applies to.

   *  *Hint Type*: The type of hint being expressed:

      -  0x01: PREFER_TRACK - Prefer a specific track (Hint Value =
         Request ID)

      -  0x02: MAX_THROUGHPUT - Cap selection at this throughput (Hint
         Value = kbps)

      -  0x03: MIN_THROUGHPUT - Floor selection at this throughput (Hint
         Value = kbps)

      -  0x04: LOCK_CURRENT - Lock current selection (Hint Value = 1 to
         lock, 0 to unlock)

   *  *Hint Value*: Interpretation depends on Hint Type.

3.3.3.  Relay Processing of Quality Hints

   When a relay receives DTS-QUALITY-HINT, it SHOULD incorporate the
   hint into its selection algorithm as follows:

apply_quality_hints(switching_set, available_bandwidth):
    hints = get_hints(switching_set.id)

    for hint in hints:
        if hint.type == PREFER_TRACK:
            # Move preferred track to front of candidates if it fits bandwidth
            preferred = find_track(hint.value)
            if preferred.throughput <= available_bandwidth:
                return preferred

        elif hint.type == MAX_THROUGHPUT:
            # Filter out tracks exceeding the cap
            candidates = [t for t in candidates if t.throughput <= hint.value]

        elif hint.type == MIN_THROUGHPUT:
            # Prefer tracks at or above the floor if bandwidth allows
            above_floor = [t for t in candidates if t.throughput >= hint.value]
            if any(t.throughput <= available_bandwidth for t in above_floor):
                candidates = above_floor

        elif hint.type == LOCK_CURRENT:
            if hint.value == 1:
                return switching_set.current_track  # No switching

    # Fall through to normal selection algorithm
    return select_preferred(candidates, available_bandwidth)

   The relay MAY ignore hints that would result in: - Buffer underrun
   (selecting quality higher than sustainable bandwidth) - Excessive
   resource consumption - Violation of publisher-specified constraints

3.3.4.  DTS-SWITCH-REQUEST Parameter

   The DTS-SWITCH-REQUEST parameter (Type 0x51) MAY appear in a
   REQUEST_UPDATE message to request immediate re-evaluation of track
   selection.

   DTS-SWITCH-REQUEST {
     Type (vi64) = 0x51,
     Length (vi64),
     Switching Set ID (vi64),
     Target Request ID (vi64),
     Switch Urgency (vi64)
   }

   *  *Switching Set ID*: The switching set to re-evaluate.

   *  *Target Request ID*: Optional (0 = no preference).  If non-zero,
      indicates the subscriber's preferred target track.

   *  *Switch Urgency*: Indicates how urgently the switch is needed:

      -  0x00: NORMAL - Switch at next convenient group boundary

      -  0x01: SOON - Switch within the next few groups if possible

      -  0x02: IMMEDIATE - Switch at the very next group boundary

3.3.5.  Relay Processing of Switch Requests

  on_switch_request(request):
      switching_set = get_switching_set(request.switching_set_id)

      if request.target_request_id != 0:
          target = find_track(request.target_request_id)
          if target.throughput <= available_bandwidth:
              # Subscriber's choice fits, honor it
              schedule_switch(switching_set, target, request.urgency)
              return

      # Re-run selection algorithm
      new_selection = run_track_selection(switching_set)

      if new_selection != switching_set.current_track:
          schedule_switch(switching_set, new_selection, request.urgency)

  schedule_switch(switching_set, target, urgency):
      if urgency == IMMEDIATE:
          switch_at_next_group_boundary(switching_set, target)
      elif urgency == SOON:
          switch_within_n_groups(switching_set, target, n=3)
      else:
          # NORMAL: switch when convenient (e.g., next IDR/key frame)
          queue_switch(switching_set, target)

3.3.7.  Relationship to SWITCH Message

   The DTS client hints provide similar subscriber influence as the
   SWITCH message (PR #1378) but with key differences:

   +===============+============================+======================+
   | Aspect        | SWITCH Message             | DTS Client Hints     |
   +===============+============================+======================+
   | Control model | Subscriber                 | Subscriber suggests, |
   |               | commands switch            | relay decides        |
   +---------------+----------------------------+----------------------+
   | Bandwidth     | Subscriber                 | Relay enforces       |
   | safety        | responsible                | constraints          |
   +---------------+----------------------------+----------------------+
   | Message       | Full SWITCH                | Lightweight hint     |
   | overhead      | message                    | parameters           |
   +---------------+----------------------------+----------------------+
   | Atomicity     | Guaranteed                 | Best-effort based on |
   |               | atomic                     | urgency              |
   +---------------+----------------------------+----------------------+
   | Relay         | SHOULD NOT                 | Hints are local to   |
   | forwarding    | forward upstream           | each hop             |
   +---------------+----------------------------+----------------------+

                                  Table 2

   DTS client hints are appropriate when: - Relay-side ABR is desired
   but subscriber input is valuable - Bandwidth safety is important
   (relay can reject unsafe hints) - Lightweight signaling is preferred
   over full SWITCH messages

   The SWITCH message remains appropriate when: - Subscriber requires
   guaranteed control over switch timing - Subscriber has better
   bandwidth knowledge than relay - Atomic transition semantics are
   required

3.4.2.  Pseudocode

on_group_arrival(Track T, Group N):
    candidates = all tracks in switching set

    while candidates not empty:
        P = select_preferred(candidates, throughput_estimate)

        if P is none:
            forward nothing; return

        if Group N of P is available (arrived or cached):
            forward Group N of P; return

        wait until (Group N of P arrives) or (timer > P.selection_time_limit)

        if Group N of P arrived:
            forward Group N of P; return
        else:
            candidates.remove(P)  # timed out, try next best

    forward nothing  # no candidates left

4.  DTS Across Multiple Switching Groups (Subscribe Namespace)

   This section describes DTS when multiple independent content streams
   must share bandwidth, such as in video conferencing where multiple
   participants each have multiple quality variants.

4.1.  Overview

   Subscribe Namespace allows a subscriber to express interest in
   multiple tracks matching a namespace prefix.  Combined with
   TRACK_FILTER, the relay can:

   1.  Select which tracks (participants) to forward based on activity
       or priority

   2.  Select which quality variant of each selected track to forward
       based on bandwidth

4.2.  Parameters

4.2.1.  TRACK_FILTER for Subscribe Namespace

   When used with SUBSCRIBE_NAMESPACE, TRACK_FILTER operates across all
   matching tracks:

   TRACK_FILTER {
     Type (vi64) = 0x29,
     Length (vi64),
     Property Type (vi64),
     MaxTracksSelected (vi64),
     MaxTracksDeselected (vi64),
     MaxTimeSelected (vi64)
   }

   *  *Property Type*: The publisher track property (e.g., Throughput
      0x4B) used for selection.

   *  *MaxTracksSelected*: Maximum number of distinct tracks (e.g.,
      participants) to forward.  This value MUST NOT exceed the
      MAX_TRACKS_SELECTED setup option value sent by the peer.  A value
      of zero is a protocol violation.

   *  *MaxTracksDeselected*: Tracks to keep in deselection buffer for
      fast re-selection.

   *  *MaxTimeSelected*: Timeout for track activity.

4.2.2.  DTS-RENDER-GROUP-ID Parameter

   The DTS-RENDER-GROUP-ID parameter (Type 0x47) groups subscriptions
   for coordinated bandwidth allocation.

   DTS-RENDER-GROUP-ID {
     Render Group ID (vi64)
   }

   Subscriptions with the same Render Group ID share a bandwidth
   allocation pool.

6.2.  Bandwidth Allocation Algorithm

   The relay allocates available bandwidth across: 1.  DTS Render Groups
   (if using Subscribe Namespace with DTS-RENDER-GROUP-ID) 2.  Switching
   Sets within each Render Group 3.  Normal (non-DTS) subscriptions

6.2.1.  Allocation Procedure

allocate_bandwidth(total_bw):
    # Step 1: Reserve bandwidth for non-DTS subscriptions
    non_dts_bw = sum(bitrate for sub in non_dts_subscriptions)
    remaining_bw = total_bw - non_dts_bw

    # Step 2: Divide remaining across Render Groups by weight
    for render_group in render_groups:
        group_weight = sum(weight for sub in render_group.subscriptions)
        render_group.allocated_bw = remaining_bw * (group_weight / total_weight)

    # Step 3: Within each Render Group, allocate to Switching Sets
    for render_group in render_groups:
        for switching_set in render_group.switching_sets:
            set_weight = sum(weight for sub in switching_set)
            switching_set.allocated_bw = render_group.allocated_bw *
                                         (set_weight / render_group.total_weight)

    # Step 4: Within each Switching Set, select quality variant
    for switching_set in all_switching_sets:
        select_quality(switching_set, switching_set.allocated_bw)

6.3.  Degradation Algorithms

   When bandwidth decreases, the relay must degrade quality.  Two
   strategies are defined:

6.3.1.  Fair Degradation

   All switching sets are degraded proportionally to their weights.

fair_degrade(switching_sets, new_total_bw):
    # Each set loses bandwidth proportionally
    for switching_set in switching_sets:
        switching_set.allocated_bw = new_total_bw *
                                     (switching_set.weight / total_weight)
        select_quality(switching_set, switching_set.allocated_bw)

6.3.2.  Weight-Ordered Degradation

   Lower-weight sets are degraded first; higher-weight sets maintain
   quality longer.

   weight_ordered_degrade(switching_sets, new_total_bw):
       # Sort sets by weight (lowest first)
       sorted_sets = sort_by_weight_ascending(switching_sets)

       remaining_bw = new_total_bw

       # Protect higher-weight sets by degrading lower-weight first
       for switching_set in sorted_sets:
           # Calculate minimum viable bandwidth for this set
           min_bw = switching_set.lowest_quality_bitrate

           if remaining_bw >= switching_set.ideal_bw:
               # Enough bandwidth for ideal quality
               switching_set.allocated_bw = switching_set.ideal_bw
           elif remaining_bw >= min_bw:
               # Partial allocation - select best fitting quality
               switching_set.allocated_bw = remaining_bw
           else:
               # Insufficient - drop to minimum or skip
               switching_set.allocated_bw = min_bw

           remaining_bw -= switching_set.allocated_bw
           select_quality(switching_set, switching_set.allocated_bw)

6.4.  Selection with Time Limits

select_with_timeout(switching_set, allocated_bw):
    candidates = switching_set.tracks
    selected = None

    while candidates not empty:
        # Find best quality that fits bandwidth
        preferred = highest_quality_under_bandwidth(candidates, allocated_bw)

        if preferred is None:
            return None  # No track fits

        if preferred.group_available():
            return preferred  # Immediately available

        # Wait for preferred track with timeout
        start_timer()

        wait_for(preferred.group OR timeout(preferred.selection_time_limit))

        if preferred.group_arrived:
            return preferred
        else:
            # Timeout - try next best
            candidates.remove(preferred)

    return None  # All candidates exhausted

6.5.  Computational Efficiency

   The allocation algorithm is designed for efficient computation:

   1.  *O(n) complexity*: Single pass through render groups and
       switching sets

   2.  *Pre-computed weights*: Total weights cached and updated only on
       subscription changes

   3.  *Incremental updates*: Only affected switching sets recalculated
       on bandwidth changes

   4.  *Bounded iterations*: Selection timeout prevents unbounded
       waiting

# Efficient weighted allocation
precompute_weights():
    total_weight = 0
    for render_group in render_groups:
        render_group.weight = sum(ss.weight for ss in render_group.switching_sets)
        total_weight += render_group.weight
    return total_weight

# O(n) allocation pass
allocate(total_bw, precomputed_total_weight):
    for render_group in render_groups:
        group_bw = total_bw * (render_group.weight / precomputed_total_weight)
        for switching_set in render_group.switching_sets:
            set_bw = group_bw * (switching_set.weight / render_group.weight)
            # Direct lookup for quality selection
            switching_set.quality = quality_table_lookup(set_bw)

      | *Switch    | Subscriber   | Relay       | Subscriber       |
      | timing*    | controls     | decides     | suggests         |
      +------------+--------------+-------------+------------------+
      | *Bandwidth | Subscriber   | Relay       | Relay enforces   |
      | safety*    | responsible  | enforces    |                  |
      +------------+--------------+-------------+------------------+
      | *Latency   | RTT to relay | Immediate   | Immediate at     |
      | to switch* |              | at relay    | relay            |
      +------------+--------------+-------------+------------------+
      | *Multi-hop | Each hop     | Each relay  | Each relay       |
      | behavior*  | switches     | decides     | decides          |
      +------------+--------------+-------------+------------------+
      | *Best for* | Known stable | Variable    | User preferences |
      |            | bandwidth    | bandwidth   | + safety         |
      +------------+--------------+-------------+------------------+

                                 Table 5

   The hybrid approach using DTS with client hints provides:

   1.  *Safety*: Relay prevents switches that would cause rebuffering

   2.  *User control*: Subscriber can express preferences (quality caps,
       preferred tracks)

   3.  *Low latency*: Relay can act immediately without RTT delay

   4.  *Graceful degradation*: Hints are advisory; relay can ignore
       unsafe requests

   layout.

│  Step 1: Track Selection (Top-2 from 4)                                 │
│  ────────────────────────────────────────                               │

│  ────────────────────────────────────────                               │

│  ────────────────────────────────────────                               │
│  P2 weight: 80, P4 weight: 40                                           │
│  Total weight: 120                                                      │
│                                                                         │

│                                                                         │

│  ────────────────────────────────────────                               │

│                                                                         │

│      - 720p needs 2500 ❌                                                │
│      - 480p needs 1000 ✓  ◄── Selected                                  │
│                                                                         │
│  Result: Forward P2@720p and P4@480p                                    │
│                                                                         │

8.4.  Degradation Scenario

┌─────────────────────────────────────────────────────────────────────────┐
│                    DEGRADATION SCENARIOS                                │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Bandwidth drops from 6000 kbps to 3000 kbps                            │
│                                                                         │
│  ═══════════════════════════════════════════════════════════════════    │
│  FAIR DEGRADATION:                                                      │
│  ═══════════════════════════════════════════════════════════════════    │
│                                                                         │
│  P2: 3000 × (80/120) = 2000 kbps → 720p (just fits)                     │
│  P4: 3000 × (40/120) = 1000 kbps → 480p                                 │
│                                                                         │
│  Both degraded proportionally.                                          │
│                                                                         │
│  ═══════════════════════════════════════════════════════════════════    │
│  WEIGHT-ORDERED DEGRADATION:                                            │
│  ═══════════════════════════════════════════════════════════════════    │
│                                                                         │
│  Sorted by weight (ascending): P4 (40), P2 (80)                         │
│                                                                         │
│  1. P4 (lowest weight): allocate minimum 1000 kbps → 480p               │
│     Remaining: 3000 - 1000 = 2000 kbps                                  │
│                                                                         │
│  2. P2 (highest weight): allocate remaining 2000 kbps → 720p            │
│                                                                         │
│  Result: P2 maintains 720p, P4 degraded to 480p                         │
│          Higher weight protected first.                                 │
│                                                                         │
│  ═══════════════════════════════════════════════════════════════════    │
│  SEVERE DEGRADATION (bandwidth = 1500 kbps):                            │
│  ═══════════════════════════════════════════════════════════════════    │
│                                                                         │
│  Weight-Ordered:                                                        │
│  1. P4: minimum 1000 kbps → 480p                                        │
│     Remaining: 500 kbps                                                 │
│  2. P2: 500 kbps insufficient for 480p (needs 1000)                     │
│     Options:                                                            │
│     a) Drop P2 entirely, or                                             │
│     b) Use priority: drop P4 (lower weight) to fit P2@480p              │
│                                                                         │
│  With priority-based decision:                                          │
│  - P2@480p (1000 kbps) + no bandwidth for P4                            │
│  - P4 dropped to maintain P2                                            │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",

   "OPTIONAL" in this document are to be interpreted as described in

   capitals, as shown here.

10.  Security Considerations

   DTS introduces relay-side decision making that could be exploited:

   *  *Resource Exhaustion*: Malicious subscribers could create many
      switching sets.  Relays SHOULD limit the number of switching sets
      per connection.

   *  *Bandwidth Manipulation*: Incorrect weight values could cause
      unfair allocation.  Relays MAY enforce weight limits or ignore
      extreme outliers.

   *  *Selection Timing Attacks*: Manipulated Selection Time Limits
      could cause excessive caching.  Relays SHOULD enforce maximum time
      limits.
