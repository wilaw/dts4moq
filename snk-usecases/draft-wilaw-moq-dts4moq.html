1. Introduction

This draft adds the capability of Dynamic Track Switching (DTS) to Media over QUIC Transport [MOQT]. Dynamic Track Switching allows a relay to dynamically switch which groups are forwarded from among a set of subscriptions. One use-case enabled by DTS is Adaptive Bitrate Streaming (ABR), in which time-aligned media tracks are switched at group boundaries based upon available throughput estimates.¶

DTS is enabled and disabled by the subscriber. The definition of the switching sets and the metadata required to implement the switching rules are defined by either the subscriber or the original punblisher.¶

2. Use Cases

This section describes several use cases that motivate Dynamic Track Switching, along with the requirements each places on publishers, subscribers, and relays.¶

2.1. Adaptive Bitrate Streaming (ABR)

2.1.1. Description

In adaptive bitrate streaming, a single media source (e.g., a live video stream) is encoded at multiple quality levels (renditions) with different bitrates and resolutions. The goal is to deliver the highest quality rendition that the network path can sustain at any given moment. When bandwidth decreases, the system should switch to a lower quality rendition to avoid rebuffering. When bandwidth increases, it should switch to a higher quality rendition to improve viewer experience.¶

2.1.2. Requirements

Original Publisher:¶

  • MUST publish multiple time-aligned renditions of the same content¶

  • MUST ensure groups across renditions are temporally aligned to enable seamless switching¶

  • SHOULD advertise throughput requirements for each rendition¶

  • SHOULD indicate which tracks belong to the same switching set (alternate group)¶

End Subscriber:¶

  • MUST subscribe to all desired renditions within a switching set¶

  • MUST indicate which subscriptions form a switching set for relay coordination¶

  • MAY specify preferences such as maximum desired quality or bandwidth constraints¶

  • SHOULD be prepared to decode any rendition within the switching set¶

Relay:¶

  • MUST track available bandwidth to each downstream subscriber¶

  • MUST select exactly one rendition per switching set to forward at any time¶

  • MUST switch renditions at group boundaries to maintain decodability¶

  • SHOULD minimize switching latency when bandwidth changes¶

2.2. Video Conferencing Grid Layout

2.2.1. Description

In a video conference with multiple participants, each participant's video may be displayed in a grid layout. When many participants are present, not all videos can be displayed at full resolution due to screen real estate and bandwidth constraints. The system needs to deliver multiple participant streams simultaneously, potentially at different quality levels based on their importance (e.g., active speaker at high quality, other participants at lower quality).¶

2.2.2. Requirements

Original Publisher:¶

  • MUST publish multiple quality renditions for their media stream¶

  • MUST ensure temporal alignment of groups across renditions¶

  • SHOULD advertise throughput requirements for each rendition¶

  • SHOULD indicate switching set membership for their renditions¶

End Subscriber:¶

  • MUST subscribe to multiple switching sets (one per participant)¶

  • MUST indicate relative importance (weight/priority) of each switching set¶

  • MAY send SUBSCRIBE_UPDATE messages to adjust priorities (e.g., when active speaker changes)¶

  • SHOULD specify total bandwidth budget or constraints¶

Relay:¶

  • MUST allocate forwarding capacity across multiple switching sets simultaneously¶

  • MUST respect subscriber-indicated weights when selecting groups to forward¶

  • MUST select one rendition per switching set based on allocated capacity¶

  • SHOULD implement degradation based on relative weight when total capacity is insufficient¶

  • SHOULD respond to SUBSCRIBE_UPDATE messages with minimal latency¶

2.3. Screen Sharing with Video

2.3.1. Description

A participant shares their screen while also transmitting camera video. The screen content may have different characteristics than camera video (e.g., higher resolution for text readability, lower frame rate acceptable). The system needs to prioritize bandwidth between screen sharing and camera video based on content type and subscriber preferences.¶

2.3.2. Requirements

Original Publisher:¶

  • MUST publish renditions for each content type (screen, camera)¶

  • MUST ensure groups are temporally aligned within each content type¶

  • SHOULD indicate content type characteristics including relative priorities per content type (e.g., screen vs camera) and per rendition within each type¶

  • SHOULD advertise throughput requirements per rendition¶

End Subscriber:¶

  • MUST subscribe to switching sets for each desired content type¶

  • MUST indicate relative weights between content types¶

  • MAY specify minimum acceptable quality for critical content (e.g., screen)¶

  • MAY send SUBSCRIBE_UPDATE messages to adjust priorities based on presentation mode¶

Relay:¶

  • MUST manage multiple switching sets with potentially different priorities¶

  • MUST select groups to forward based on content type priorities¶

  • SHOULD respect minimum quality thresholds indicated in subscription parameters¶

  • SHOULD degrade lower-priority content before higher-priority content¶

2.4. VR/AR Streaming

2.4.1. Description

Virtual and augmented reality applications require streaming high-resolution immersive content while adapting to available bandwidth. Two key scenarios benefit from DTS: foveated rendering where quality varies based on gaze direction, and multi-layer environments where different scene elements have different quality requirements.¶

In foveated rendering, a 360-degree video is divided into tiles. The tile where the user is currently looking (determined by eye tracking) receives highest quality, while peripheral tiles receive lower quality. As the user's gaze shifts, bandwidth allocation must dynamically shift between tiles.¶

In multi-layer VR environments, background scenery may be rendered at lower quality while interactive foreground objects receive higher quality, with priorities adjusting based on user proximity and interaction state.¶

2.4.2. Requirements

Original Publisher:¶

  • MUST publish multiple quality renditions for each tile or scene layer¶

  • MUST ensure temporal alignment across tiles and quality levels¶

  • SHOULD advertise throughput requirements per tile/quality combination¶

  • SHOULD indicate tile spatial relationships or layer hierarchy¶

End Subscriber:¶

  • MUST subscribe to all tiles within the field of view¶

  • MUST send SUBSCRIBE_UPDATE messages to adjust priority weights based on gaze direction or interaction state¶

  • SHOULD specify gaze tile with significantly higher weight than peripheral tiles¶

  • MAY specify minimum acceptable quality for peripheral tiles to avoid visible artifacts¶

Relay:¶

  • MUST respond rapidly to SUBSCRIBE_UPDATE messages containing updated priority weights¶

  • MUST adjust group forwarding decisions across tile subscriptions when priority weights change¶

  • SHOULD maintain subscriptions to adjacent tiles at lower priority to enable smooth transitions¶

  • MUST switch forwarded renditions at group boundaries to ensure decodability¶

2.5. Cloud Gaming

2.5.1. Description

Cloud gaming services stream rendered game video from servers to players. The video stream must adapt to network conditions while balancing resolution, frame rate, and latency based on game type and player preferences. Different game genres have different requirements: fast-paced action games prioritize frame rate and low latency, while strategy games may prioritize resolution.¶

Additionally, different regions of the game screen may have different importance: the HUD (heads-up display) with critical game information may need guaranteed quality, while the main game world adapts to remaining bandwidth.¶

2.5.2. Requirements

Original Publisher:¶

  • MUST publish multiple quality renditions of game video¶

  • MUST ensure consistent frame pacing across quality levels¶

  • SHOULD separate HUD/overlay into distinct tracks when bandwidth guarantees are needed¶

  • SHOULD advertise throughput and latency characteristics per rendition¶

  • MAY indicate game type hints affecting quality/latency tradeoffs¶

End Subscriber:¶

  • MUST subscribe to game video switching set and any separate HUD tracks¶

  • MUST indicate priorities (e.g., HUD guaranteed, game video adaptive)¶

  • MAY specify preferences for frame rate vs resolution tradeoffs¶

  • SHOULD report input latency requirements to influence relay decisions¶

Relay:¶

  • MUST prioritize forwarding groups for guaranteed streams (HUD) before adaptive allocation¶

  • MUST select game video rendition to forward based on remaining capacity¶

  • SHOULD minimize switching latency to maintain gameplay responsiveness¶

  • MUST switch forwarded renditions at group boundaries to ensure decodability¶

2.6. Live Sports Multi-View

2.6.1. Description

Live sports broadcasts offer multiple camera angles: main game camera, sideline cameras, aerial views, and isolated player cameras. Viewers may want to watch multiple angles simultaneously, with the ability to prioritize different views. A stats overlay stream provides real-time game information. Bandwidth must be allocated across these streams based on viewer preferences that may change during the event (e.g., switching focus to replay angle).¶

2.6.2. Requirements

Original Publisher:¶

  • MUST publish multiple quality renditions for each camera angle¶

  • MUST ensure temporal synchronization across all camera angles¶

  • SHOULD advertise throughput requirements per angle/quality combination¶

  • MAY publish stats overlay as separate low-bandwidth guaranteed stream¶

End Subscriber:¶

  • MUST subscribe to desired camera angles and stats overlay¶

  • MUST indicate relative priority/weight for each camera angle¶

  • MAY send SUBSCRIBE_UPDATE messages to adjust priorities (e.g., boost replay camera during highlights)¶

  • SHOULD specify minimum acceptable quality for primary view¶

Relay:¶

  • MUST select groups to forward based on subscriber-indicated weights¶

  • MUST maintain temporal sync when forwarding multiple angles¶

  • SHOULD respond to SUBSCRIBE_UPDATE messages promptly for seamless view switching¶

  • MUST switch forwarded renditions at group boundaries to ensure decodability¶

2.7. Teleoperation and Robotics

2.7.1. Description

Remote operation of robots, drones, or industrial equipment requires streaming multiple video feeds with different importance levels. The primary control camera (showing the manipulation task) requires highest quality and lowest latency. Secondary cameras providing situational awareness can accept lower quality. Sensor telemetry streams compete for bandwidth with video feeds.¶

3. Subscribe parameters

We introduce two new message parameters to enable Dynamic Track Switching.¶

3.1. The SWITCHING-SET-ASSIGNMENT parameter

The SWITCHING-SET-ASSIGNMENT parameter (Parameter Type 0x41) MAY appear in a SUBSCRIBE or REQUEST_UPDATE message. This parameter assigns the accompanying subscription to a DTS switching set and specifies a waiting time-limit. The parameter body is serialized as follows:¶

SWITCHING-SET-ASSIGNMENT {
  Switching set ID (vi64),
  [Throughput threshold (vi64),
  Selection time limit (vi64)]
}
¶

  • Switching set ID - an integer specifying a switching set. The value zero is reserved to indicate no switching set.¶

  • Throughput threshold - the minimum throughput, expressed in integer kilobits per second, necessary to select this subscription. This value MUST be omitted if the Switching set ID is zero.¶

  • Selection time limit - the maximum amount of time, in milliseconds, which a relay MUST wait after the arrival of the first candidate group in a switching group, before this subscription is disqualified as the preferred selection. This value MUST be omitted if the Switching set ID is zero.¶

3.2. The DTS-ACTIVATION parameter.

The DTS-ACTIVATION parameter (Parameter Type 0x43) MAY appear in a SUBSCRIBE or REQUEST_UPDATE message. This parameter enables or disables dynamic track switching for a specified switching set. The parameter body is serialized as follows:¶

DTS-ACTIVATION {
  Switching set ID (vi64),
  State (1)
}
¶

  • Switching set ID - an integer referencing a previously defined switching set.¶

  • State - a value of 1 activates dynanmic switching for the specified switching set and a value of 0 deactivates it.¶

4. Workflow

4.1. Client workflow

  1. The client decides, through a catalog or other out-of-band mechanism, which of a set of tracks it wishes to enable for DTS.¶

  2. The client selects an integer identifier to label this set. This identifier MUST be unique within the MOQT connection.¶

  3. For each track, it issues a SUBSCRIPTION and appends a SWITCHING-SET-ASSIGNMENT parameter. Within that parameter, it communicates the set identifier, the throughput threshold and the time limit.¶

  4. On the last SUBCRIPTION, the client also appends the DTS-ACTIVATION parameter and sets it value to 1. Dynamic track selection is now active for the switching set.¶

To disable dynamic track selection for a given switching set, the client sends a DTS-ACTIVATION parameter with a state value of 0 on a REQUEST-UPDATE message. This action leaves all subscriptions in that switching set still active, but with a Forward state of 0. To re-enable dynamic track selection for that set, the client sends a DTS-ACTIVATION parameter with a state value of 1 on a REQUEST-UPDATE message.¶

To remove one track from a switching set, while leaving the other tracks active, the client issues a REQUEST_UPDATE message with the request ID referencing the subscription it wishes to remove and a SWITCHING-SET-ASSIGNMENT parameter with a Switching set ID of zero.¶

To add a new track to an existing switching set, the client issues a SUBSCRIPTION and appends a SWITCHING-SET-ASSIGNMENT parameter, with the Switching set ID poiniting at the existing switching set.¶

4.2. Relay workflow

  1. Upon receiving a SWITCHING-SET-ASSIGNMENT parameter, the relay adds the subscription to the specified switching set, creating the switching set if it does not yet exist. The Forward state of the subscription is set to zero.¶

  2. Upon receiving a DTS-ACTIVATION parameter with a state of 1, the relay beings active track selection. Active track selection implies that the relay monitor the incoming new groups as well as maintain an estimate of the throughput available in the connection. This throughput estimate SHOULD be applicable over the maximum Group duration of the tracks being switched.¶

  3. When the first Object 0 of new Group N of track T arrives at the relay, the relay selects the preferred track to forward from the switching set. The preferred track is the track with the highest throughput threshold smaller than or equal to the current throughput estimate. The relay sets the Forward state to 1 for this track and to 0 for all other tracks in the switching set. If no tracks in the switching set satisfy this condition, then all tracks are set to a Forward state of 0. No content will be delivered until the decision is re-evaulated at the next Gorup boundary.¶

  4. If the track T happens to be the preferred track, then the relay forwards all Objects from that Group and no futher evaluations are required until Group N+1 arrives. If the track T is not the preferred track, then the relay caches the Group of track T and starts a selection timer.¶

  5. If Group N of the preferred track arrives while the selection timer > selection time limit of that track, then the relay forwards the preferred track, the timer can be stopped and no further evaluations are necessary.¶

  6. If Group N of the preferred track has not arrived by the time the selection timer reaches the selection time limit, then the relay selects a new preferred track by removing the previously preferred track from its candidate list and re-applying the logic of step 3. If Group N of the new preferred track has already arrived, then it is served from cache, irrespective of its Selection time limit. If Group N of the new preferred track has not yet arrived then the selection process repeats at step 6.¶
